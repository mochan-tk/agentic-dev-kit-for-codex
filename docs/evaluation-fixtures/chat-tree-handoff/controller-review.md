# Chat-tree handoff forward review

This packet is authored teaching/check material, not a runtime protocol or a
captured native-app replay. It does not authorize real app or GitHub operations.
The packet's `NOT_RUN` status describes the reusable fixture; actual trials
have separate dated Issue/PR receipts and must not rewrite this input as proof.

Give an independent candidate only the exact bound Skill and `input.json`.
Keep this controller/reviewer note, source diff, tests and expected findings
out of its context. Ask it to handle each scenario independently. It may read
those two inputs and return proposed records/actions, but may not modify
files, invoke app tools or contact services. Do not supply the intended fix.

Record the Skill/input/prompt SHA-256 values, delivered scenario sequence,
actual candidate response binding, observed tool actions, review findings and
limitations in a bounded Issue/PR receipt. Do not publish raw transcripts or
private environment/app metadata. Review meaning and proposed operations,
not matching phrases. A hypothetical layout is not an observed sidebar.

| Scenario | Review the actual response for |
|---|---|
| Initial handoff | Explicit offer, pending decision record and continued authorized execution; no implied display permission. |
| Owner reply | Apply decision with scope/authority link carried Epic -> Task -> supervisor -> worker; projection responsibility; proposed preorder puts supervisor beneath Task #121 and worker beneath supervisor, before Task #122. |
| Owner decline | Durable declined record reused in handoff; no proposed fork/message/rename/order operation. |
| Surface unavailable | Durable unavailable record with reason, distinct from decline; no guessed app API or workaround, subagent execution continues. |
| Shared sort question | The wider Recents/project effect is explained; no shared preference mutation or claim that recency sorting establishes the requested layout. |
| Partial display failure | Preserve the known returned ID and ambiguous result; stop affected mutations without retrying/duplicating the fork or replacing the still-running executor. |

Across scenarios, claim/plan/dispatch examples must retain the actual
executing supervisor and worker references and isolated branch/worktree.
Display-only forks receive no execution prompt and do not count as workers.
No scenario may borrow authority or observations from another. Report any
failure and repair only the affected instructions before a fresh exercise.

Keep these evidence levels separate in the trial receipt:

- Observed candidate handoff/decision behavior: report what it actually wrote.
- Proposed preorder: manual review of the candidate's hypothetical layout.
- Native API mutation: `NOT_RUN` in this exercise.
- Native title/project readback: `NOT_RUN`; supplied scenario data is not capture.
- Native manual-order readback: `NOT_RUN`.
- Visual confirmation: `NOT_RUN`.
